# Пилот проверки договора услуг — API 1.28

Первое направление — возмездное оказание услуг в предпринимательских отношениях.
Пилот формирует черновик для юриста. Смешанные договоры, специальные режимы и
непредпринимательский профиль возвращаются на уточнение квалификации.

## Сценарий в интерфейсе

1. Подключитесь к `/workspace` индивидуальным токеном, выберите дело.
2. Загрузите и сохраните договор; при необходимости добавьте приложения и
   переписку. Сценарий включает весь сохранённый текст выбранного договора,
   максимум 20000 символов. Превышение возвращает явную ошибку без обрезки.
3. В форме «Сопоставить документы» задайте вопрос и дату ситуации. Раскройте
   «Пилот: договор услуг между предпринимателями», включите режим, выберите
   сохранённый договор и ответьте на четыре вопроса. «Не установлено» не
   превращается в отрицательный ответ.
4. Подготовьте источники норм и досье редакций на дату, передайте их другому
   проверяющему и выберите необходимые нормы в форме. Приложение учитывает запись
   проверки, но не удостоверяет квалификацию человека. Нельзя использовать один
   документ одновременно как договор и выбранную редакцию нормы.
5. Без фактов возвращается `needs_facts`, при конфликте профиля —
   `needs_qualification`, без выбранных норм — `needs_sources`. Модель не вызывается.
6. Режим «Показать фрагменты без модели» возвращает только демонстрацию цитаты.
   Для рабочего вызова выключите его. Для удалённой модели нужны одновременно
   разрешение запроса и серверное разрешение передачи документов; настройки
   автоматически не меняются.
7. Проверьте разбор в предпросмотре и скачайте сохранённый сервером UTF-8 Markdown.
   Перед скачиванием повторно проверяются доступ, хеши источников и состояние
   выбранных редакций. При смене параметров, пользователя или дела предпросмотр
   сбрасывается; сохранённый снимок остаётся в базе дела.
8. При необходимости включите обучающую память и сначала просмотрите подборку.
   Память использует одобренные исправленные примеры только этого дела на ту же
   дату. Контрольные эталоны исключайте из подбора. Подробности: `docs/LEARNING_MEMORY.md`.

## Структура вывода

Каждый вывод содержит вид, оценку, объяснение применимости, следующий шаг и
дословные цитаты с документами, SHA-256, смещениями и страницами фрагментов.

| Вид | Минимальные технические требования |
|---|---|
| Наблюдение | Цитата выбранного договора |
| Кандидат на правовой риск | Цитата договора и цитата источника с выбранной редакцией на дату |
| Предполагаемое противоречие | Цитаты минимум двух разных документов, включая договор |
| Недостающие сведения | Связь с цитатой договора и объяснение, что запросить |

Это проверка структуры и точности цитирования. Совпадение цитаты не доказывает,
что норма подтверждает вывод, правильно выбрана статья или учтены все исключения.
`semantic_support_verified`, `verified`, `lawyer_reviewed`, `legal_acceptance`
остаются `false`. Пустой список выводов не объявляет договор безопасным.

Один ответ содержит до 20 выводов и до 8 цитат на вывод; Markdown ограничен
512 КиБ без скрытого усечения доказательств. Недоверенный текст выводится как
текст, а в Markdown помещается в блоки с защищёнными границами.

## API

Используется существующий `POST /workspace/ask` с полями:

```json
{
  "matter_id": "<дело>",
  "question": "Какие условия оплаты и приёмки требуют проверки?",
  "analysis_mode": "services_pilot",
  "contract_document_id": "<сохранённый договор>",
  "as_of": "2025-06-30",
  "facts": {
    "both_businesses": true,
    "paid_activity": true,
    "mixed_contract": false,
    "special_regime": false
  },
  "editions": [],
  "demo": true,
  "allow_cloud": false
}
```

Пустой `editions` намеренно возвращает `needs_sources`. Допускается до трёх
ссылок `{act_id, provision}`; каждая выбирается существующим механизмом редакций.
Неоднозначный период, отозванная проверка и неподходящая дата останавливают запрос.
Общий режим анализа документов остаётся доступен без новых полей.

### Точная привязка текста нормы

В интерфейсе «Подготовить редакцию нормы» выберите документ нормы и документ,
подтверждающий период (они могут совпадать), укажите реквизиты, даты и точные
цитаты. Сохранение создаёт черновик; одобрение записывает другой эксперт через
обычную очередь материалов. Пустая дата окончания означает открытую границу,
а не автоматически подтверждённое действие на текущую дату.

`POST /workspace/evidence/add` для `kind=edition` принимает дополнительное поле
`payload.provision_quote`: полный текст выбранной нормы, 10–10000 символов,
встречающийся в `document_id` ровно один раз. Повторяющуюся цитату необходимо
расширить. Поле хранится в неизменяемом досье как `provision_evidence` с документом,
его хешем и смещениями. Подтверждение полноты остаётся заявлением и предметом
независимой проверки; приложение не распознаёт границы статьи автоматически.

Пилот требует такую привязку для каждой выбранной редакции. Карточки прежнего
формата сохраняются и доступны общему режиму; пилот возвращает HTTP 409
`edition_provision_required`. Для перехода создайте новое досье с цитатой,
проверьте его независимо и отзовите одобрение заменяемой карточки: два одобренных
досье той же нормы с пересекающимися периодами по-прежнему блокируют выбор.

Полный привязанный текст попадает в контекст независимо от поисковых слов.
`selected_editions` содержит `provision_start` и `provision_end`. Цитата риска
должна полностью находиться внутри границ хотя бы одной выбранной нормы.
Фрагмент из соседней статьи того же документа и цитата, пересекающая границу,
не засчитываются как нормативное основание. Если один документ содержит несколько
выбранных норм, в выводе сохраняются только ссылки, содержащие конкретную цитату.
Границы включаются в Markdown для проверки.

Это обеспечивает буквальную привязку, но не доказывает юридическую применимость,
официальность введённого URL или правильность решения эксперта.

`POST /workspace/analysis/validate` получает `matter_id`, `as_of`, `documents`
из `{document_id, sha256}` и `editions` из `selected_editions` ответа. Возвращает
только актуальность технического контекста. Он не удостоверяет подлинность
находящегося у клиента отчёта и не подписывает юридические выводы. В журнал
записывается факт проверки без текстов и секретов.

### Сохранённый отчёт

Начиная с API 1.27 сервер сохраняет результат HTTP-запроса пилота в той же базе
дела как `analysis_report`. Сохранение происходит после завершения рабочего
процесса в одной транзакции с повторной проверкой доступа, хешей документов,
состояния проверок редакций и журналом. Отменённый запрос или поздний отзыв
доступа не создаёт снимок. Локальный вызов `matter_research.answer` без HTTP-сервера
ничего не сохраняет.

Ответ `/workspace/ask` дополнительно содержит `report_id`,
`report_snapshot_sha256`, `report_saved=true` и `report_authenticity_verified=true`.
Для скачивания используйте `POST /workspace/analysis/read`:

```json
{
  "matter_id": "<дело>",
  "report_id": "<report_id из ответа пилота>",
  "markdown_sha256": "<markdown_sha256 из того же ответа>"
}
```

Сервер проверяет доступ к делу, принадлежность снимка, хеш сохранённого payload,
хеш Markdown, неизменность источников и точных записей одобрения редакций.
Возвращаются сохранённые `markdown`, `filename`, их отпечатки и
`context_current=true`. Клиентские тексты и произвольные поля не принимаются.
Неверный отпечаток, новый отзыв/повторное одобрение или пересекающаяся редакция
блокируют выдачу. После перезапуска сервера снимок доступен по тем же реквизитам.
Отчёты доступны участникам с текущим доступом к этому делу; право на чужое дело
не даёт доступа к снимку.

Интерфейс скачивает именно байты ответа `/workspace/analysis/read`, а не копию
Markdown из памяти страницы. `/workspace/evidence/read` не выдаёт снимки в обход
этой проверки; они не появляются в очереди материалов и не принимают одобрений
через `/workspace/evidence/review`.

Снимок хранится без автоматического срока удаления, содержит данные дела и входит
в резервные копии SQLite. Существующая схема БД не меняется. Восстановление
сохраняет байты и записи проверок; старые токены остаются отключёнными по обычным
правилам восстановления. Отозванная до создания копии проверка не становится
действующей после восстановления. Откат к старой резервной копии не восстанавливает
события после её создания; перед эксплуатацией проверьте актуальные права и отзывы.

`report_authenticity_verified=true` означает совпадение с серверным снимком,
а не электронную подпись или независимое заверение. Это не защита от администратора,
который может заменить всю БД и пересчитать хеши, и не юридическая приёмка.
`digital_signature` и `legal_acceptance` остаются `false`.

## 25 заданий для независимой приёмки

В разделе экспертных заданий нажмите «Добавить 25 заданий по услугам».
Задания `SERV-P01`–`SERV-P25` импортируются отдельно; прежний импорт 90 задач
не меняется. Повторный импорт не дублирует записи.

Каждое задание содержит синтетический договор, вопрос, иногда дополнительный
документ, заявленные обстоятельства, темы поиска, рубрику проверки и недопустимый
вывод. Поле `approved_legal_answer` пусто, одобрений нет. Темы и рубрики не являются
утверждёнными правилами права. Реальных проверенных юридических эталонов этим
изменением не добавлено.

Темы: объём и приложения, цена и налоговая оговорка, оплата и аванс, сроки,
приёмка и возражения, третьи лица, отказ сторон, ответственность и неустойка,
изменение тарифа, электронные сообщения, полномочия, конфиденциальность,
исторические даты, смешанный договор, специальный режим, потребительский профиль
и команды внутри недоверенного документа.

Эксперт должен подобрать реальные первичные источники и редакции, ввести
ожидаемый ответ, обязательные риски и точные цитаты. Затем другой проверяющий
принимает или возвращает материал через существующую очередь. Для оценки реальных
ответов используйте корректность, пропущенные риски и неподтверждённые утверждения;
не заменяйте эти показатели числом технических тестов.

## Проверки и открытые условия

```sh
python -m unittest test_service_pilot test_workspace_report_ui test_benchmark_tasks -v
python scripts/pilot_acceptance.py --live
```

Тестовый HTTP-сценарий проходит через настоящий дочерний процесс и локальный
синтетический OpenAI-совместимый сервер. Это проверка транспорта, схемы, цитат
и доступа, а не настоящей модели и не юридического качества.

Поиск дополнительных документов использует локальный FTS5 и ограниченный список
связанных слов: цена/стоимость/тариф, предоплата/аванс, отказ/расторжение/прекращение,
неустойка/штраф/пени, уведомление/извещение, приёмка/акт, оплата/платёж и срок/период.
Это поисковые подсказки, а не утверждение юридической равнозначности терминов.
Исходный запрос получает больший вес; ранги объединяются, затем предпочтение
отдаётся разным документам. Длинный договор не должен занимать все позиции
вместо подходящей переписки. Отбирается до 96 документов-кандидатов на запрос,
до 12 фрагментов на поисковый проход и до восьми фрагментов после объединения;
сам выбранный договор включается полностью отдельно. Достижение лимита отражается
в `retrieval.candidate_limit_reached`, полнота поиска всегда не подтверждена.
Поздние судебные кандидаты отсекаются до окончательного отбора контекста.

Контроли поиска: `python -m unittest test_services_retrieval -v`. На 12 специально
подготовленных синтетических запросах расширение находит целевой документ,
который исходный текстовый запрос не находил. Это не оценка точности на реальных
делах, не проверка всех лишних результатов и не юридическая приёмка.
Результаты и границы: [SERVICES_RETRIEVAL_ACCEPTANCE_2026-11-09.json](SERVICES_RETRIEVAL_ACCEPTANCE_2026-11-09.json).

Семантический поиск с эмбеддингами,
полные истории законодательства и судебных цепочек этим этапом не добавлены.
Полнота исходного DOCX/PDF после извлечения, приложения и смысловая поддержка
каждого вывода требуют проверки. Настоящая модель, браузер и независимый юрист
остаются отдельными условиями пилота.
