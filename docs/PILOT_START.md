# Подготовка пилота одной командой

В API 1.25 доступна [экспертная оценка ответов и сравнение прогонов](QUALITY_REVIEW.md).
Текущий отчёт запуска: [QUALITY_REVIEW_READINESS_2026-11-09.json](QUALITY_REVIEW_READINESS_2026-11-09.json).
Проверка кода: [QUALITY_REVIEW_ACCEPTANCE_2026-11-09.json](QUALITY_REVIEW_ACCEPTANCE_2026-11-09.json).

Для первого направления доступен [сценарий договора услуг](SERVICES_PILOT.md)
с отдельными 25 заданиями для независимой проверки. Предыдущий технический
отчёт API 1.24: [SERVICES_PILOT_READINESS_2026-11-09.json](SERVICES_PILOT_READINESS_2026-11-09.json).

Из корня проекта выполните:

```sh
python scripts/pilot_acceptance.py
```

Команда последовательно собирает один JSON-отчёт: целостность нормативного
корпуса, повторное извлечение архивных PDF, демо-API, рабочее пространство,
восстановление резервной копии, логику интерфейса и доступность браузерного
прогона. Каждый этап запускается отдельно с ограничением времени. Содержимое
документов, ключи, адреса провайдеров и произвольные ошибки в отчёт не включаются.

Используются временные синтетические учётные записи, документы и БД. Существующая
рабочая база не открывается; её доступы, данные и файлы не изменяются. Обычный
запуск не делает запросов к модели, поиску или официальным сайтам. Подготовка
выходного отчёта не создаёт `.env` и не меняет настройки передачи документов.

## Как читать отчёт

| Поле | Что оно подтверждает |
|---|---|
| `local_checks_passed` | Пройдены шесть локальных этапов: данные, PDF, демо-API, дела, восстановление, логика UI |
| `browser_acceptance` | Пройден существующий Chromium smoke демоинтерфейса; полноценная браузерная приёмка рабочего пространства отдельно не подтверждается |
| `live_acceptance_passed` | Реальные модель и поиск прошли встроенные технические проверки с синтетическими входами |
| `automated_checks_passed` | Все перечисленные автоматические этапы прошли; это не разрешение на ввод в эксплуатацию |
| `production_ready`, `legal_acceptance` | Всегда `false`: инструмент не подписывает юридическую или эксплуатационную приёмку |
| `manual_gates` | Требуется независимая проверка юристом и проверка целевого развёртывания |
| `external_requests_attempted` | Были ли обращения к провайдерам; `null` означает неизвестный результат live-процесса, например после таймаута |

Итоговый `status=failed` и код выхода **1** означают ошибку, неполный или
повреждённый отчёт. `status=blocked` и код **2** означают незакрытые условия
приёмки. Поскольку ручные условия инструмент не подтверждает, код **0** не
выдаётся даже при успешных автоматических проверках. Пропущенный live-этап,
отсутствующий Chromium или недостающие инструменты не становятся успехом.

## Реальная модель и поиск

Подготовьте `.env` по [инструкции запуска](LOCAL_LIVE_START.md). Ключи задаются
на машине запуска, а не публикуются в репозитории. Затем явно запустите:

```sh
python scripts/pilot_acceptance.py --live
```

Этот режим может расходовать запросы API. Если локальные этапы не прошли или
обязательные настройки отсутствуют, внешняя проверка не запускается. Для передачи
технического примера договора удалённой модели сохраняется существующее требование
`ALLOW_CLOUD_DOCUMENTS`; инструмент не включает его автоматически. Согласие в
настройках не заменяет основания обработки реальных пользовательских данных.

Локальный этап ограничен 120 секундами, браузерный — 210, live — 630. Это
последовательные бюджеты этапов, а не общий дедлайн всей команды. На POSIX
используется существующее завершение группы процессов; переносимость полного
сценария на Windows не принята. Уже принятые провайдером запросы не отзываются.

## Перед первым реальным делом

1. Ограничьте пилот выбранным типом договоров и кругом участников.
2. Получите проверенные источники и редакции для этого направления; примите
   реальные контрольные задачи независимым юристом.
3. Проверьте интерфейс рабочего пространства в браузере на компьютере и телефоне.
4. На целевой машине проверьте индивидуальный доступ, HTTPS при сетевом запуске,
   хранение секретов, сроки удаления и резервное копирование с восстановлением.
5. Согласуйте обязательную проверку результата юристом перед использованием.

Docker не обязателен при прямом запуске Python. Этот инструмент не строит образ,
не настраивает сервер и не принимает рабочую инфраструктуру. Полные инструкции
по данным и восстановлению: [рабочее пространство](PROFESSIONAL_WORKSPACE.md)
и [резервные копии](WORKSPACE_RECOVERY.md).

Пример фактического отчёта текущего этапа:
[PILOT_READINESS_2026-11-09.json](PILOT_READINESS_2026-11-09.json).

Первоначальный прогон API 1.23 от 9 ноября 2026: все шесть локальных этапов прошли — 454 извлечения,
90 синтетических заданий, семь PDF/90 страниц, 26 демо + 54 workspace + 9 recovery
HTTP-проверок и 21 сценарий логики UI. Chromium отсутствует; обязательные
настройки модели и поиска отсутствуют. Внешние запросы не выполнялись.
Полный технический прогон: 578 тестов запущено, 577 прошли, один тест русского
OCR пропущен из-за отсутствия языковых данных. 12 новых проверок контролируют
неполные отчёты, таймауты, запрет неявных live-запросов и границы приёмки.
