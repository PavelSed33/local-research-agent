# Локальный запуск и техническая приёмка без GitHub Actions

Используется рабочая версия ветки `feature/legal-p0-coverage`. Пока PR не объединены, старый `main` не содержит все эти команды и проверки. Нужен Python 3.10 или новее. Проверка запускается на компьютере или сервере, где будет работать агент; Docker для этого пути не требуется.

## 1. Подготовить настройки

Из корня проекта выполните:

```sh
python scripts/acceptance.py --init-env
```

Команда создаёт `.env` по `.env.example` только при отсутствии файла. Существующий файл с ключами не перезаписывается. Новый файл на POSIX-системах создаётся с правами 0600. Затем заполните в локальном `.env`:

- `LLM_API_KEY` — ключ выбранного OpenAI-совместимого сервиса модели.
- `LLM_MODEL` — точный идентификатор модели этого сервиса.
- `LLM_BASE_URL` — адрес его OpenAI-совместимого API либо адрес локальной модели.
- `TAVILY_API_KEY` — ключ поиска Tavily.

Для локальной модели без требования настоящего API-ключа текущий клиент всё равно требует непустое значение `LLM_API_KEY`; это техническое требование клиента, не подтверждение авторизации локального сервиса. Совместимость конкретного сервера проверяется запросом, не предполагается по его названию.

Шаблонные значения считаются отсутствующими настройками. Файлы `.env` исключены из Git и контекста Docker. Ключи задаются в окружении запуска; отчёт не выводит их, название модели, тексты ответов провайдеров и произвольные сообщения исключений.

Для передачи договоров удалённой модели отдельно требуется `ALLOW_CLOUD_DOCUMENTS=true`. Проверочный сценарий использует только встроенный текст технического договора без персональных данных, но не обходит этот запрет. Сама настройка не является юридическим основанием обработки пользовательских документов. Для loopback-модели действует существующий локальный режим.

## 2. Проверить локальную работу

```sh
python scripts/acceptance.py
```

Создаётся изолированный сервер на свободном loopback-порту с новым случайным токеном. Выполняются 15 HTTP-проверок: файлы интерфейса, варианты вопросов о договоре, демоисследование, договор, реквизиты, сравнение, судебные материалы, правовое покрытие, анкета данных и удаление специально созданной тестовой сессии. Это не обращение к пользовательскому работающему серверу и не удаление его истории.

Деморежим не обращается к внешним провайдерам. `status=passed` в этом режиме не означает готовности реальной модели, поиска, юридической базы или браузера.

## 3. Выполнить реальные проверки

```sh
python scripts/acceptance.py --live --timeout-seconds 900
```

Последовательность:

1. Сначала локальные 15 HTTP-проверок. Если они не проходят, внешние запросы не начинаются.
2. Проверяются наличие настроек и допустимость адресов. Если настроек нет, возвращается `blocked`, а не успешная приёмка.
3. Реальная модель должна вернуть ожидаемый JSON на простой технический запрос. Отдельно реальный Tavily должен вернуть материалы по техническому правовому запросу.
4. После успешных проб проверяются `/review`, `/extract`, `/review/legal`, `/case-law/check` и `/ask` с `demo=false`. Если передача документов не разрешена, три документных маршрута остаются `blocked`; настройка автоматически не включается.
5. Для извлечения требуется хотя бы одна сумма из встроенного примера. У судебного поиска фиксируется число выбранных актов: корректный ответ без найденных актов подтверждает форму ответа, но не достаточность правовых доказательств.

Режим `--live` действительно расходует запросы API. Полный цикл `/ask` может делать несколько обращений к модели, поиску и официальным источникам; подписка на интерфейс чата сама по себе не задаёт эти настройки. Не передаются документы с диска, личные дела и история рабочего сервера.

Для всего процесса задан предел 600 секунд по умолчанию, допустимы 10–1800 секунд. При превышении родительский процесс завершает дочерний процесс, включая его API-обработчики. После таймаута HTTP-запроса новые рабочие сценарии не запускаются. Уже принятый внешним провайдером запрос этим не отзывается. Это ограничение инструмента приёмки, не реализация отмены запросов в обычном рабочем API.

## 4. Прочитать результат

| Результат | Значение | Код завершения |
|---|---|---:|
| `passed` | Все обязательные технические проверки выбранного режима завершены | 0 |
| `blocked` | Нет настроек или разрешения передачи документов; проверка неполна | 2 |
| `failed` | Ошибка провайдера, неверная форма ответа, локальный сбой или дедлайн | 1 |

`live_acceptance_passed=true` возможен только в реальном режиме после всех обязательных проверок. Пустой, неполный или потерянный отчёт не становится успешным. `legal_acceptance` и `browser_acceptance` всегда false: сценарии не проверяют юридическую правильность реальных задач, смысловую полноту и визуальные взаимодействия в браузере.

Временные результаты сохраняются в закрытом временном каталоге и убираются родительским процессом, включая завершение по дедлайну. Рабочие ключи не передаются в аргументах командной строки. Сведения об ошибках ограничены известной причиной, типом исключения и HTTP-кодом; тела ошибок провайдеров не печатаются.

## 5. Запустить рабочий интерфейс

После технической проверки выполните:

```sh
python api.py
```

Для стандартного локального режима откройте `http://127.0.0.1:8080/`. При заданном `API_TOKEN` введите его в интерфейсе. Включённый в UI деморежим нужно выключить для реальных запросов. Для внешнего интерфейса API_TOKEN обязателен; это не заменяет настройку защиты публичного сервера.

После проверки реальных ответов остаются юридические эталоны, источники/редакции и приёмка юристом. Наличие ключей и успешных HTTP-запросов не закрывает эти задачи.
