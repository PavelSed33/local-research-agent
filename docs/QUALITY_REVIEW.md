# Экспертная оценка ответов и сравнение версий — API 1.25

Цель — получить измеримые человеческие оценки реальных ответов, отдельно от
технических тестов. Приложение хранит запись оценки; оно не удостоверяет
квалификацию проверяющего или факт настоящего запуска модели.

## Подготовить принятый эталон

1. Импортируйте задания нужного направления в дело. Для услуг доступны 25
   отдельных синтетических задач; это заготовки, не утверждённые ответы.
2. Эксперт подбирает первичные источники и редакции, вводит ожидаемый ответ,
   обязательные риски, недопустимые выводы и дословные цитаты.
3. Другой пользователь с ролью `reviewer` и доступом к делу проверяет материал
   через существующую очередь. Самоодобрение не допускается.
4. Откройте задание заново. При действующем одобрении появляется форма
   «Оценить ответ по принятому эталону».

## Записать оценку

Введите понятную метку версии/прогона, например `pilot-v1`, и полный оцениваемый
ответ. Сопоставьте его с текущим эталоном и источниками, выберите правильность
от 0 до 4, отметьте пропущенные риски, посчитайте неподтверждённые утверждения и
обоснуйте оценку. Поля не заполняются автоматически от имени юриста.

Ответ и заметка сохраняются в базе дела. Не вставляйте секреты или сведения
чужого дела. Маркировка версии вводится человеком; она не доказывает, какая
модель реально подготовила ответ. Не сравнивайте результаты разных задач так,
будто это испытание одной и той же работы.

Записать оценку может только `reviewer` с доступом к делу и при действующем
одобрении эталона. Читатель дела может смотреть агрегированные показатели.
Смена задания, дела или пользователя очищает форму и блокирует использование
запоздавших ответов. Если запись уже ушла на сервер до смены контекста,
обновите статистику перед повторной отправкой: смена формы не отменяет запись.

## Как сравнивать версии

Нажмите «Показать качество и сравнение прогонов». Отчёт показывает:

- количество оценок, уникальных эталонов и текстов ответов;
- среднюю правильность 0–4;
- долю пропущенных обязательных рисков;
- число неподтверждённых утверждений;
- группы по меткам прогонов и отдельный расчёт на общих эталонах всех меток;
- оценки, исключённые после изменения проверки или из-за отсутствия привязки.

Общие эталоны определяются по идентификаторам неизменяемых материалов, а не
по совпадению названия задания. Если пересечения нет, общий сравнительный
расчёт не строится. При трёх метках требуется пересечение всех трёх наборов.
Средние считаются по записям оценок: несколько ответов или проверяющих на одну
задачу дают несколько записей. Это не среднее по уникальным делам и не
статистическое доказательство превосходства модели. Автоматического победителя
и допуска в эксплуатацию нет.

## Защита от устаревшей проверки

Новая оценка сохраняет `benchmark_review_sha256`: хеш конкретной записи
одобрения эталона на момент оценки. При отзыве или смене этой записи оценка
исключается из текущей статистики. Повторное одобрение того же эталона не
возвращает прежние оценки автоматически.
Отпечаток включает уникальный ID записи проверки: совпадение дат не делает
две разные записи одним одобрением. Подготовленные до обновления приложения
снимки редакций могут потребовать повторного формирования из-за нового отпечатка.

Старые записи без привязки сохраняются в БД, но учитываются отдельно как
`excluded_without_review_binding`; инструмент не присваивает им новую проверку.
Схема SQLite не меняется, файлы базы не мигрируют и не перезаписываются.
Хеш привязки не является электронной подписью или защитой от оператора,
имеющего полный доступ к файлу БД.

Один эксперт не может дважды оценить один и тот же текст по тому же материалу,
даже под другой меткой. Для новой версии эталона создайте новый черновик задания
с отдельным одобрением. Прежние записи остаются историей; не обходите защиту
дубликатов косметическими изменениями ответа.

## API

`POST /workspace/evaluations/record` использует прежние поля и необязательный
`run_label` длиной 1–80 символов. Без метки используется `untagged`. В ответе
есть хеш текста ответа и привязка к проверке. `legal_acceptance=false`.

`POST /workspace/evaluations/metrics` получает `matter_id`. Помимо общих
показателей возвращает `by_run_label`, `shared_benchmark_count`,
`shared_benchmark_comparison` и счётчики исключений. Тексты ответов и заметки
в этот агрегированный ответ не включаются.

## Проверки

```sh
python -m unittest test_quality_scoring test_workspace_report_ui -v
node scripts/test_quality_scoring.cjs
python scripts/pilot_acceptance.py --live
```

Технические сценарии используют только временные синтетические эталоны,
ответы и проверки. Они не создают принятых юридических задач пользователя.
Реальная модель, независимый юрист, проверенные редакции и рабочая инфраструктура
остаются отдельными условиями пилота.
