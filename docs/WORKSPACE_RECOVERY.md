# Резервное копирование базы дел и восстановление

API 1.23. Добавлены локальные команды оператора, работающие с БД рабочего
пространства. Это доработка эксплуатационной защиты, а не юридическая приёмка
или гарантия полной защиты персональных данных.

## Что входит в копию

Снимок SQLite включает учётные записи, хеши токенов, дела, права участников,
документы и оригиналы, индекс поиска, экспертные материалы, версии карточек,
задания, проверки, оценки и журнал. Используется SQLite backup API, поэтому
копируются согласованные данные с учётом WAL, а не только основной файл.
Работающая исходная база не перезаписывается и не отключается.

Архив содержит два элемента: `workspace.sqlite3` и `manifest.json`. Manifest
связывает SHA-256 и размер БД со счётчиками записей, версией схемы и концом
цепочки аудита. ZIP не зашифрован. В нём есть тексты дел и персональные данные;
права 0700/0600 не заменяют шифрование диска или отдельного защищённого хранилища.
Используйте runtime/backups либо отдельную закрытую директорию вне репозитория.
Дополнительно из Git исключены верхнеуровневые backups/recovery, файлы SQLite
и архивы с окончанием .workspace-backup.zip. Произвольное имя ZIP вне этих
директорий не становится автоматически безопасным для публикации.

Нет HTTP-маршрута экспорта/восстановления всей БД. Команды рассчитаны на
доверенного оператора с локальным доступом к файлу сервера, а не на обычного
администратора приложения. Не открывайте эти команды через веб-интерфейс.

## Создание и проверка копии

Подготовьте принадлежащую оператору закрытую директорию:

```sh
umask 077
mkdir -m 700 -p runtime/backups
python scripts/manage_workspace.py backup \
  --db runtime/workspace.db --output runtime/backups/snapshot-2026-11-09.zip
```

Команда возвращает JSON с `snapshot_sha256`, счётчиками и концом аудита, без
текстов дел или токенов. Сохраните отпечаток отдельно от архива в доверенном
журнале оператора. Он требуется для восстановления. Существующий файл назначения
не заменяется; для каждой копии выбирайте новое имя.

```sh
python scripts/manage_workspace.py verify-backup \
  --input runtime/backups/snapshot-2026-11-09.zip \
  --expected-sha256 <отпечаток из доверенного журнала>
```

Без expected-sha256 команда verify-backup проверяет внутреннюю целостность,
но это не удостоверяет происхождение архива. Хеши и manifest не являются
цифровой подписью: оператор с полным доступом может переписать их. Отпечаток,
сохранённый отдельно до инцидента, нужен для проверки ожидаемого снимка.

Копирование и проверка сначала выполняются в закрытой временной директории.
Публикуется полностью проверенный файл с запретом перезаписи. Предусмотрены
ограничение БД 256 МиБ, архива 300 МиБ и 30-секундный бюджет SQLite-копирования
и SQL-проверок. Файловое сжатие и чтение дополнительно ограничены размером;
жёсткий общий wall-clock-дедлайн для всех файловых операций не заявляется.

## Что проверяется

- Текущая схема приложения, включая индексы и защитные триггеры; исходный
  файл не инициализируется и не «чинится» перед проверкой.
- SQLite integrity_check, внешние ключи и членство владельца дела.
- Хеши текстов, оригиналов, материалов, снимков заданий и оцениваемых ответов.
- Точность и принадлежность цитат документам дела, границы страниц.
- Покрытие поискового индекса фрагментами исходного текста, отсутствие чужих
  или осиротевших фрагментов.
- Привязка проверок к материалам, связность версий судебных карточек,
  отсутствие циклов и корректный корень цепочки.
- Полная цепочка хешей журнала.

Проверки не устанавливают правильность юридических выводов, обоснованность
прав доступа или полноту обезличивания. Схема должна соответствовать этой
версии приложения; неизвестные изменения/триггеры отклоняются. Восстановление
между произвольными версиями приложения не реализовано.

## Восстановление в новый файл

Восстановление всегда использует новое имя БД. Нельзя направлять его в файл
работающей базы, существующий файл или путь с SQLite sidecar-файлами.
Отпечаток архива обязателен; данные не извлекаются по именам из ZIP на файловую
систему. Входной архив сначала копируется в закрытую область, затем проверяется.

```sh
mkdir -m 700 -p runtime/recovery
python scripts/manage_workspace.py restore \
  --input runtime/backups/snapshot-2026-11-09.zip \
  --db runtime/recovery/recovered.db \
  --expected-sha256 <отпечаток из доверенного журнала>
```

Все прежние токены в новой БД отключаются. Иначе копия могла бы вернуть ключи,
которые уже отозваны в более свежей рабочей базе. Записывается событие
`workspace_restored_tokens_revoked`, затем снова проверяется целостность.
Исходная база и её ключи не изменяются.

**Пользователи и права восстанавливаются на дату снимка.** Изменения доступа
после этой даты автоматически не известны: их нужно сверить с журналом
оператора и политикой доступа до выдачи новых токенов и переключения сервиса.
Ни один пользователь не получает новую роль автоматически.

Сначала восстановите доступ существующему активному администратору:

```sh
python scripts/manage_workspace.py recover-admin-token \
  --db runtime/recovery/recovered.db --user-id <существующий id администратора>
```

Команда показывает новый секрет один раз: защищайте stdout как секрет и не
сохраняйте его в публичных логах. Используйте известный ID из первоначальной
настройки; при его отсутствии доверенный оператор может проверить учётные
записи непосредственно в локальной БД. Не создавайте фиктивные повышения роли.
Если активного администратора нет, автоматического восстановления его роли
этими командами не производится.

После проверки учётной записи и прав отдельного участника:

```sh
python scripts/manage_workspace.py recover-user-token \
  --db runtime/recovery/recovered.db --user-id <существующий id участника>
```

Это также локальная команда оператора. Она выдаёт ключ существующей активной
учётной записи и сохраняет её роль. В журнале указывается `local-recovery`
и событие `token_reissued_local`; это не заявление о входе самого пользователя.
Через веб-API возможность выдавать ключи других участников не добавлена.

## Проверка и переключение

```sh
python scripts/manage_workspace.py verify-audit --db runtime/recovery/recovered.db
WORKSPACE_DB="$PWD/runtime/recovery/recovered.db" API_HOST=127.0.0.1 python api.py
```

verify-audit теперь работает только с существующим файлом и дополнительно
проверяет целостность данных. Ошибочный путь не создаёт пустую «успешную» БД.

Поднимайте восстановленную БД сначала как отдельный экземпляр, проверьте
авторизацию, права, документы и поиск. Не запускайте два разных файла под одним
производственным адресом одновременно. Переключение работающего сервиса и
принятие решения об актуальности данных остаются действиями оператора.
Сам модуль не останавливает сервис и не меняет WORKSPACE_DB.

Хеш restored_db_sha256 относится к моменту публикации восстановленного файла.
Дальнейшая выдача токенов, действия пользователей и открытие приложения в WAL
изменяют файл; это ожидаемо. Для текущей БД используйте проверку данных/журнала,
а не сравнение с хешем файла до первого запуска.

## Границы хранения

Копируется только SQLite рабочего пространства, включая оригиналы в BLOB.
Репозиторий, модели, секреты провайдеров, внешние папки результатов, временные
сессии и активные задачи в этот архив не входят. Содержимое БД без шифрования,
SSO, автоматическая ротация/удаление копий и внешняя неизменяемая копия аудита
не реализованы. Обнаружение полностью переписанной оператором цепочки без
доверенного внешнего отпечатка не гарантируется.

Файлы создаются с правами 0600, конечная директория должна принадлежать
оператору и не давать доступа группе/остальным. Общая директория отклоняется;
программа не меняет права существующих общих директорий. Проверки выполнены
в Linux/POSIX; эквивалентная защита ACL Windows отдельно не принята.

## Проверки

```sh
python -m unittest test_workspace_backup test_backup_acceptance test_packaging -q
python scripts/backup_acceptance.py
python -m unittest discover -q
```

Сквозной сценарий использует временные учётные записи и отдельную восстановленную
БД: старые ключи отклоняются, новые работают, наблюдатель читает/ищет, но не пишет,
посторонний получает отказ; исходная БД остаётся работоспособной. Проверены WAL,
оригиналы, 90 черновых заданий, версии карточек, повреждения и отсутствие
перезаписи. Секреты тестовых учётных записей в отчёт не включаются.

Официальная документация механизма:
[Python sqlite3 Connection.backup](https://docs.python.org/3/library/sqlite3.html#sqlite3.Connection.backup).

Результат текущего прогона: **565 тестов, 26 прежних + 54 workspace + 9 recovery
HTTP-проверок**. Отдельно повторены 11 регрессий архивов и отказов — они также прошли.
[WORKSPACE_RECOVERY_ACCEPTANCE_1_23_2026-11-09.json](WORKSPACE_RECOVERY_ACCEPTANCE_1_23_2026-11-09.json).
Всё восстановление выполнялось на временных синтетических данных, не на рабочей
базе пользователя. Браузер, Docker, внешняя модель и юридическая приёмка отдельно
не подтверждены.
