# Юридический ИИ-помощник по законодательству РФ

Локальный прототип, который принимает правовой вопрос, ищет нормы в правовых источниках, отдельно проверяет последние изменения и готовит ответ со ссылками.

## Что умеет

- формировать до 5 первоначальных поисковых запросов;
- искать материалы через Tavily по заданному списку правовых сайтов;
- оценивать полноту найденных норм и выполнять до двух циклов дополнительного поиска;
- **при каждом запуске отдельно искать последние изменения, новые редакции, даты вступления в силу и сведения об утрате силы**;
- искать судебную практику по вопросу отдельным этапом (экспериментально: через веб-поиск по `kad.arbitr.ru`, `vsrf.ru`, `sudact.ru`, подборка выборочная);
- проверять, что упомянутые в ответе статьи действительно есть в текстах найденных источников;
- указывать дату проверки изменений;
- формировать ответ только на основании найденных материалов;
- проверять обязательные разделы, номера цитат и отсутствие посторонних ссылок;
- один раз исправлять ответ, если автоматическая проверка обнаружила ошибки;
- **самопроверку готового ответа**: модель отдельным проходом ищет противоречия между разделами и неподтверждённые выводы, при замечаниях ответ исправляется и повторно проходит структурную проверку (сбой этапа не отменяет ответ, запись — в журнале `self_reflection`);
- сохранять ответ в Markdown и подробный журнал в JSON;
- принимать запросы по HTTP API (`POST /ask`, `POST /review`, `POST /extract`, `POST /diff`, `POST /penalty`, `POST /check`, `POST /timeline`, `POST /draft`, `POST /triage`, `POST /duty`, `POST /export`, `POST /protocol`, `POST /scoring`, `GET /health`, `GET /openapi.json`) для интеграции в «завод агентов»;
- проверять договоры по чек-листу рисков с дословными цитатами пунктов (каждая цитата проверяется на вхождение в текст договора);
- сводить проверку договора в оценку 0–100 с вердиктом (можно подписывать / требует доработки / не рекомендуется): веса за риски и пробелы фиксированы и считаются кодом, число воспроизводимо;
- извлекать из договора реквизиты в структурированный JSON: стороны с ИНН/ОГРН, суммы, сроки, неустойки и подсудность (ИНН и ОГРН дополнительно проверяются по контрольным суммам);
- принимать договор не только текстом, но и файлом DOCX (текст извлекается стандартной библиотекой, без сторонних зависимостей; таблицы — спецификации и цены — сохраняются строками «| … | … |» на своём месте; PDF честно отклоняется с подсказкой);
- сравнивать две редакции договора (lite-redlining): построчный список изменений added/removed/changed и unified diff — детерминированно, без LLM;
- собирать протокол разногласий по двум редакциям: таблицу «пункт / редакция А / редакция Б / предложение» с дословным контролем редакций кодом — готовый формат для переговоров, экспортируется в DOCX;
- рассчитывать неустойку (договорную и проценты по ст. 395 ГК РФ) детерминированным модулем с разбивкой по периодам действия ключевой ставки ЦБ — кодом, без LLM;
- экспортировать любой результат (проект документа, проверку) в DOCX: файл собирается стандартной библиотекой, таблицы и заголовки сохраняются;
- рассчитывать госпошлину (ст. 333.19 и 333.21 НК РФ): имущественный иск, судебный приказ, неимущественные иски, апелляция и кассация; шкала выбирается по дате подачи — действующая редакция или редакция до 08.09.2024 — кодом, без LLM;
- готовить проекты документов (претензия, ответ на претензию, допсоглашение, уведомление) с плейсхолдерами и проверкой ссылок на договор — статус всегда draft;
- собирать хронологию дела из переписки и первички: события извлекает модель, даты и дословность цитат проверяет код, сортировка по датам — кодом;
- проверять контрагента по ИНН через открытый сервис ФНС (ЕГРЮЛ/ЕГРИП): наименование, ОГРН, КПП, дата регистрации, руководитель, прекращение деятельности + детерминированные признаки риска (свежая регистрация, прекращение деятельности, ИНН не найден, контрольная сумма ИНН);
- маршрутизировать входящие юридические запросы: категория (договор/спор/комплаенс), срочность, риск и рекомендуемый эндпоинт — значения только из допустимых перечислений, «галлюцинированная» категория не пройдёт;
- вести реестр договоров по папке файлов: CSV со сторонами, ИНН, суммами и сроками + отчёт «что истекает в ближайшие N дней»;
- проводить пакетный аудит договорной базы: каждый файл папки получает оценку 0–100, итог — CSV и сводный отчёт «худшие договоры сверху» со средней оценкой по портфелю;
- отдавать метрики наблюдаемости в `/health`: аптайм, число запросов и ошибок и среднее время ответа по каждому эндпоинту;
- работать в демонстрационном режиме без ключей и внешних запросов.

## Важные ограничения

Агент не «знает все законы» и не заменяет полноценную профессиональную правовую базу. Он ищет доступные тексты при каждом обращении. Результат является информационной справкой, а не индивидуальной юридической консультацией. Автоматическая проверка не гарантирует актуальность нормы: важные решения необходимо проверять по официальным текстам и при необходимости обсуждать с юристом.

По умолчанию поиск ограничен доменами:

- `pravo.gov.ru` — официальный интернет-портал правовой информации;
- `www.consultant.ru` — справочные тексты и редакции КонсультантПлюс;
- `www.garant.ru` — правовые материалы Гаранта.

Список можно изменить через `LEGAL_SEARCH_DOMAINS`. Наличие сайта в списке не означает, что каждый найденный документ является официальной или действующей редакцией.

Судебная практика ищется по списку `COURT_SEARCH_DOMAINS` (по умолчанию `kad.arbitr.ru,vsrf.ru,sudact.ru`). Веб-поиск по судебным сайтам даёт выборочные результаты: для полноценного анализа практики нужна профессиональная правовая база.

## Требования

- Python 3.10 или новее;
- для реальной работы — ключ языковой модели с OpenAI-совместимым API и ключ Tavily;
- для демонстрационного запуска ключи не нужны;
- сторонние Python-библиотеки не требуются.

## Быстрая проверка

```bash
python agent.py "Какие документы нужны для регистрации ИП" --demo
```

В Windows при необходимости используйте `py` вместо `python`.

В папке `результаты` появятся:

- `ответ-<дата>.md` — правовой ответ, дата проверки, предупреждение и источники;
- `журнал-<дата>.json` — запросы, материалы, дополнительные циклы и отдельная запись о проверке изменений.

Демонстрационный режим использует условные материалы и не даёт реального правового заключения.

## Настройка реальной работы

1. Скопируйте `.env.example` в `.env`.
2. Укажите ключи и модель:

```dotenv
LLM_API_KEY=ваш_ключ
LLM_MODEL=название_доступной_модели
LLM_BASE_URL=https://api.openai.com/v1
TAVILY_API_KEY=ваш_ключ_tavily
LEGAL_SEARCH_DOMAINS=pravo.gov.ru,www.consultant.ru,www.garant.ru
COURT_SEARCH_DOMAINS=kad.arbitr.ru,vsrf.ru,sudact.ru
```

Если используется другой OpenAI-совместимый сервис, замените `LLM_BASE_URL` на базовый адрес без `/chat/completions` в конце.

3. Запустите помощника:

```bash
python agent.py "Может ли работодатель изменить график без согласия работника" --queries 3 --sources 8
```

Параметры:

- `--queries` — от 1 до 5 первоначальных запросов;
- `--sources` — от 1 до 10 источников;
- `--output-dir` — другая папка для результатов;
- `--demo` — локальная проверка без API.

## HTTP API

Файл `api.py` поднимает HTTP-сервис поверх той же логики агента — это универсальный способ подключить помощника к «заводу агентов» или любой другой системе. Обязательная проверка последних изменений выполняется при каждом запросе, как и в консольном режиме.

Запуск:

```bash
python api.py
```

Эндпоинты:

- `GET /health` — проверка работоспособности. Возвращает `status`, версию сервиса и флаги `llm_configured` / `tavily_configured`, чтобы «завод агентов» видел готовность конфигурации, а также метрики `metrics`: аптайм в секундах, по каждому эндпоинту — число запросов (`count`), ошибок 4xx/5xx (`errors`) и среднее время ответа (`avg_ms`). Счётчики живут в оперативной памяти и обнуляются при перезапуске.
- `POST /ask` — правовой вопрос. Тело запроса:

```json
{
  "question": "Может ли работодатель изменить график без согласия работника",
  "queries": 3,
  "sources": 6,
  "demo": false
}
```

Поля `queries` (1–5), `sources` (1–10) и `demo` необязательны. Необязательное поле `session_id` (1–64 символа: латиница, цифры, дефис) включает краткосрочную память: повторные вопросы с тем же `session_id` учитывают контекст предыдущих вопросов сессии. Память хранится только в оперативной памяти сервера, записи живут 1 час, на сессию сохраняется до 10 последних пар «вопрос — краткий ответ». Ответ:

```json
{
  "answer": "# …маркдаун-ответ с источниками…",
  "sources": [{"title": "…", "url": "…"}],
  "checked_on": "2026-11-06",
  "disclaimer": "Информационная справка, а не индивидуальная юридическая консультация…",
  "demo": false,
  "session_id": null,
  "report_file": "…",
  "journal_file": "…"
}
```

- `POST /review` — проверка договора. Тело запроса:

```json
{
  "document": "полный текст договора",
  "demo": false
}
```

Вместо текста можно передать файл DOCX в base64 — поле `"document_base64": "UEsDB…"`. PDF не поддерживается: сохраните документ как DOCX или передайте текст. Ответ:

```json
{
  "status": "draft",
  "summary": "общий вывод",
  "risks": [{"category": "односторонние права", "severity": "high", "quote": "дословная цитата из договора", "comment": "в чём риск", "recommendation": "что изменить"}],
  "missing_clauses": ["отсутствующее существенное условие"],
  "checked_on": "2026-11-06",
  "disclaimer": "…",
  "demo": false,
  "review_repaired": false
}
```

Поле `status` всегда равно `"draft"`: результат — проект для проверки юристом, а не финальное заключение (human-in-the-loop). Каждая цитата проверяется на дословное вхождение в текст договора; при нарушениях результат один раз отправляется на исправление. Текст договора не сохраняется на диск. Та же проверка доступна из командной строки: `python review.py договор.txt` (с `--demo` — без ключей).

- `POST /extract` — извлечение реквизитов из договора. Тело запроса такое же, как у `/review` (текст или `document_base64` с DOCX). Ответ:

```json
{
  "status": "draft",
  "parties": [{"role": "арендодатель", "name": "ООО «…»", "inn": "7707083893", "ogrn": "1027700132195", "quote": "дословная цитата с реквизитами"}],
  "amounts": [{"label": "арендная плата", "value": "100 000 руб.", "currency": "RUB", "quote": "дословная цитата"}],
  "dates": [{"label": "окончание действия", "date": "31.12.2026", "quote": "дословная цитата"}],
  "penalties": [{"label": "неустойка", "rate": "0,1% в день", "quote": "дословная цитата"}],
  "term": {"duration": "до 31.12.2026", "quote": "дословная цитата"},
  "jurisdiction": {"court": "Арбитражный суд города Москвы", "quote": "дословная цитата"},
  "warnings": ["ИНН … не проходит контрольную сумму — проверьте, возможна опечатка в договоре."],
  "checked_on": "2026-11-06",
  "disclaimer": "…",
  "demo": false,
  "extraction_repaired": false
}
```

Цитаты и идентификаторы (ИНН/ОГРН) проверяются на дословное вхождение в текст договора, ИНН и ОГРН дополнительно сверяются по контрольным суммам: несоответствие попадает в `warnings` как возможная опечатка в договоре. Из командной строки: `python extract.py договор.docx` (поддерживаются .txt и .docx; с `--demo` — реквизиты извлекаются регулярными выражениями без ключей).

## Реестр договоров

Файл `registry.py` собирает реестр по папке договоров: каждый .txt/.docx проходит извлечение реквизитов, результат складывается в CSV (разделитель «;», открывается в Excel), а даты в ближайшие N дней — в отдельный отчёт:

```bash
python registry.py папка_с_договорами --demo --days 30
```

В папке `реестр` (меняется через `--output-dir`) появятся:

- `реестр.csv` — файл, стороны, ИНН, суммы, даты, срок действия, подсудность, предупреждения;
- `истекающие-договоры.md` — даты в ближайшие N дней (по умолчанию 30) с указанием файла и оставшихся дней.

PDF пропускается с предупреждением; ошибка по одному файлу не останавливает обход папки (строка попадает в реестр с текстом ошибки).

- `POST /diff` — сравнение двух редакций договора (lite-redlining). Детерминированно, без LLM и внешних запросов. Тело запроса:

```json
{
  "document_a": "старая редакция (текст или document_a_base64 с DOCX)",
  "document_b": "новая редакция (текст или document_b_base64 с DOCX)"
}
```

Ответ:

```json
{
  "status": "draft",
  "summary": {"added": 1, "removed": 0, "changed": 1, "unchanged": 3},
  "changes": [{"type": "changed", "old": "старая строка", "new": "новая строка"}],
  "diff": "unified diff построчно",
  "checked_on": "2026-11-06",
  "disclaimer": "…"
}
```

Из командной строки: `python redline.py старая.txt новая.txt` (поддерживаются .txt и .docx).

- `POST /penalty` — расчёт неустойки. Детерминированно, кодом на Decimal, без LLM и внешних запросов. Два режима: `contractual` (договорная: сумма × ставка % в день × дни) и `key_rate` (проценты по ст. 395 ГК РФ: сумма × ключевая ставка ЦБ / 365 × дни, с разбивкой по периодам действия ставок). Тело запроса:

```json
{
  "mode": "key_rate",
  "amount": "365 000 руб.",
  "start_date": "01.08.2026",
  "end_date": "10.08.2026"
}
```

Для режима `contractual` обязательно поле `"rate_per_day": "0,1"`. Поле `end_date` необязательно — по умолчанию дата расчёта. Ответ — итог с разбивкой по периодам:

```json
{
  "status": "draft",
  "mode": "key_rate",
  "period": {"from": "2026-08-01", "to": "2026-08-10", "days": 10},
  "breakdown": [{"from": "2026-08-01", "to": "2026-08-10", "days": 10, "rate": "14% годовых (ключевая ставка ЦБ)", "penalty": "1 400 руб. 00 коп."}],
  "total": "1 400 руб. 00 коп.",
  "formula": "сумма × ставка ЦБ / 365 × дни просрочки (по периодам действия ставок), ст. 395 ГК РФ",
  "warnings": [],
  "checked_on": "2026-11-06",
  "disclaimer": "…"
}
```

Справочник ключевой ставки встроен в код (с 19.09.2016 по последнее решение ЦБ) и проверен по публикациям Банка России; период после последнего известного решения сопровождается предупреждением. Дни считаются со дня, следующего за сроком исполнения, по день фактической уплаты включительно. Из командной строки: `python penalty.py 365000 01.08.2026 10.08.2026 --mode key_rate`.

- `POST /check` — проверка контрагента по ИНН. Запрашивает открытый сервис ФНС `egrul.nalog.ru` (ключ не нужен) и возвращает сведения ЕГРЮЛ/ЕГРИП плюс детерминированные признаки риска. Тело запроса:

```json
{
  "inn": "7707083893",
  "demo": false
}
```

Ответ:

```json
{
  "status": "draft",
  "inn": "7707083893",
  "company": {"name": "ПАО «СБЕРБАНК РОССИИ»", "ogrn": "1027700132195", "kpp": "773601001", "registered_on": "16.08.2002", "terminated_on": "", "head": "…", "region": "Г.Москва"},
  "risk_level": "low",
  "risk_flags": [{"code": "fresh_registration", "severity": "medium", "comment": "…"}],
  "checks": {"egrul": "performed", "arbitration": {"performed": false, "reason": "…"}, "sanctions": {"performed": false}, "mass_registration": {"performed": false}},
  "warnings": [],
  "checked_on": "2026-11-06",
  "disclaimer": "…",
  "demo": false
}
```

Признаки риска считаются кодом: ИНН не найден в ЕГРЮЛ (high), прекращение деятельности (high), регистрация менее 12 месяцев назад (medium), несовпадение контрольной суммы ИНН (предупреждение). Если задан `TAVILY_API_KEY`, дополнительно выполняется выборочный поиск упоминаний контрагента на `kad.arbitr.ru`. Ограничения открытых источников указаны честно: полный адрес, массовость регистрации и недостоверность сведений доступны только в выписке ЕГРЮЛ (PDF), санкционные списки открытого бесплатного API не имеют — эти проверки помечаются как не выполненные, а не имитируются. Из командной строки: `python check.py 7707083893` (с `--demo` — без внешних запросов).

- `POST /timeline` — хронология дела из материалов (переписка, первичка). Тело запроса:

```json
{
  "materials": [
    {"name": "письмо-1.txt", "text": "текст письма…"},
    {"name": "акт.docx.txt", "text": "текст акта…"}
  ],
  "demo": false
}
```

Модель извлекает события с датами и дословными цитатами; код проверяет формат каждой даты, вхождение цитаты в указанный источник и существование источника, затем сортирует датированные события. Ответ:

```json
{
  "status": "draft",
  "events": [{"date": "15.01.2026", "event": "…", "source": "письмо-1.txt", "quote": "дословная цитата"}],
  "undated_events": [{"date": "", "event": "событие без даты", "source": "…", "quote": "…"}],
  "events_count": 2,
  "materials": ["письмо-1.txt", "акт.docx.txt"],
  "checked_on": "2026-11-06",
  "disclaimer": "…",
  "timeline_repaired": false
}
```

События без даты попадают в `undated_events` и не угадываются. Из командной строки: `python timeline.py письмо-1.txt письмо-2.docx --demo` (поддерживаются .txt и .docx).

- `POST /draft` — проект юридического документа. Типы: `claim` (претензия), `claim_response` (ответ на претензию), `amendment` (допсоглашение), `notification` (уведомление). Тело запроса:

```json
{
  "type": "claim",
  "facts": "По договору аренды № 12 арендатор не оплатил сентябрь и октябрь, долг 200 000 руб. Нужна претензия с оплатой в 10 дней.",
  "contract": "текст договора-основания (необязательно)",
  "demo": false
}
```

Код проверяет обязательные блоки по типу документа и дословность цитат из договора в поле `references`; недостающие данные модель обязана оставлять плейсхолдерами `[номер договора]`, а не выдумывать — их количество возвращается в `warnings`. Ответ:

```json
{
  "status": "draft",
  "doc_type": "claim",
  "title": "Претензия о взыскании задолженности",
  "document": "# ПРЕТЕНЗИЯ\n\n…текст проекта…",
  "references": [{"quote": "дословная цитата из договора"}],
  "warnings": ["В проекте N плейсхолдер(ов) для заполнения…"],
  "checked_on": "2026-11-06",
  "disclaimer": "…",
  "draft_repaired": false
}
```

Из командной строки: `python draft.py claim --facts ситуация.txt --contract договор.docx --demo`.

- `POST /triage` — маршрутизация входящего обращения. Тело запроса:

```json
{
  "text": "Срочно! Контрагент не оплатил счёт, готовим претензию и иск.",
  "demo": false
}
```

Модель классифицирует обращение один проходом, код проверяет, что все значения — из допустимых перечислений, а эндпоинт соответствует категории (contract → /review, /extract, /draft; dispute → /timeline, /penalty, /draft, /ask; compliance → /check, /ask; general → /ask). Ответ:

```json
{
  "status": "draft",
  "category": "dispute",
  "urgency": "high",
  "risk": "high",
  "summary": "Суть запроса одним предложением",
  "recommended_endpoint": "/timeline",
  "checked_on": "2026-11-06",
  "disclaimer": "…",
  "triage_repaired": false
}
```

Из командной строки: `python triage.py обращение.txt --demo` (в демо-режиме — классификация по ключевым словам без внешних вызовов).

- `POST /duty` — расчёт госпошлины. Тело запроса:

```json
{
  "court": "arbitration",
  "mode": "claim",
  "amount": "500 000",
  "filing_date": "06.11.2026"
}
```

`court` — `arbitration` (ст. 333.21 НК РФ) или `general` (суды общей юрисдикции, ст. 333.19); `mode` — `claim` (имущественный иск, по умолчанию), `court_order` (судебный приказ, 50%), `non_property`, `appeal`, `cassation` (для фиксированных — поле `applicant`: `individual`/`organization`). Шкала выбирается по `filing_date`: заявления, поданные после 08.09.2024, считаются по редакции ФЗ № 259-ФЗ, ранее — по старой. Ответ:

```json
{
  "status": "draft",
  "court": "arbitration",
  "mode": "claim",
  "amount": "500 000 руб. 00 коп.",
  "duty": "30 000 руб. 00 коп.",
  "formula": "10 000 руб. 00 коп. + 5% × (500 000 руб. 00 коп. − 100 000 руб. 00 коп.)",
  "article": "подп. 1 п. 1 ст. 333.21 НК РФ",
  "scale": "редакция с 08.09.2024 (ФЗ № 259-ФЗ)",
  "checked_on": "2026-11-06",
  "disclaimer": "…"
}
```

Из командной строки: `python duty.py 500000 --court arbitration` (или `python duty.py --court general --mode non_property --applicant individual`).

- `POST /export` — экспорт результата в DOCX. Тело запроса:

```json
{
  "title": "Претензия по договору № 12",
  "document": "# ПРЕТЕНЗИЯ\n\n| Месяц | Сумма |\n| Сентябрь | 100 000 руб. |\n\n- оплатить долг"
}
```

Ответ — `filename`, `docx_base64` и `size_bytes`: файл собран стандартной библиотекой (заголовки, списки, таблицы), готов к открытию в Word. Типичная связка: взять `document` из ответа `/draft` или текст отчёта `/review` и передать в `/export`. Из командной строки: `python export.py документ.md -o документ.docx`.

- `POST /protocol` — протокол разногласий по двум редакциям договора. Тело запроса — как у `/diff` (`document_a` / `document_b` или `*_base64`), плюс необязательные `party_a` / `party_b` (названия сторон) и `demo`. Сверку делает код (как в `/diff`), комментарии и формулировки предложений — модель; код проверяет, что обе редакции в каждой строке дословно входят в соответствующие тексты. Ответ:

```json
{
  "status": "draft",
  "rows": [
    {
      "point": "п. 1",
      "edition_a": "дословная редакция стороны А",
      "edition_b": "дословная редакция стороны Б",
      "comment": "предложение юриста"
    }
  ],
  "protocol_markdown": "# ПРОТОКОЛ РАЗНОГЛАСИЙ\n\n| Пункт | Редакция «А» | …",
  "summary": {"added": 1, "removed": 1, "changed": 1, "unchanged": 2},
  "checked_on": "2026-11-06",
  "disclaimer": "…"
}
```

`protocol_markdown` готов к передаче в `/export` для получения DOCX. Из командной строки: `python protocol.py старая.txt новая.txt --party-a Арендодатель --party-b Арендатор --demo`.

- `POST /scoring` — сводная оценка договора 0–100. Тело запроса такое же, как у `/review`. Риски и недостающие условия находит модель (с контролем цитат), оценку считает код: риск high −20, medium −10, low −5 (не более −70), каждое недостающее условие −15 (не более −45). Ответ:

```json
{
  "status": "draft",
  "score": 55,
  "verdict": "Договор требует доработки: есть существенные риски или пробелы.",
  "verdict_color": "yellow",
  "deductions": [{"reason": "Риск (high): односторонние права", "weight": -20}],
  "weights": {"base": 100, "severity": {"high": 20, "medium": 10, "low": 5}},
  "summary": "…",
  "risks": [],
  "missing_clauses": [],
  "checked_on": "2026-11-06",
  "disclaimer": "…"
}
```

Вердикт: 80–100 — green (можно подписывать с правками), 50–79 — yellow (требует доработки), 0–49 — red (подписывать не рекомендуется). Из командной строки: `python scoring.py договор.docx --demo`.

### Пакетный аудит договоров

Файл `audit.py` проверяет всю папку договоров скорингом (как `POST /scoring`) и собирает итог:

```bash
python audit.py папка_с_договорами --demo
```

Результат — два файла в папке `аудит/` (меняется флагом `--output-dir`): `аудит.csv` (файл, оценка, вердикт, число рисков по severity, недостающие условия; открывается в Excel) и `аудит.md` (сводка: средняя оценка по портфелю, худшие договоры сверху, разбор самого проблемного, ошибки обработки). PDF пропускается с предупреждением; ошибка по одному файлу не останавливает обход.

- `GET /openapi.json` — машинное описание API (OpenAPI 3.0) для интеграции с оркестраторами и «заводом агентов». Открыт без токена, как и `/health`.

Проверка без ключей:

```bash
curl -s http://127.0.0.1:8080/health
curl -s -X POST http://127.0.0.1:8080/ask \
  -H "Content-Type: application/json" \
  -d '{"question": "Какие документы нужны для регистрации ИП", "demo": true}'
curl -s -X POST http://127.0.0.1:8080/review \
  -H "Content-Type: application/json" \
  -d '{"document": "ДОГОВОР АРЕНДЫ… полный текст …", "demo": true}'
curl -s -X POST http://127.0.0.1:8080/extract \
  -H "Content-Type: application/json" \
  -d '{"document": "ДОГОВОР АРЕНДЫ… полный текст …", "demo": true}'
```

Настройки API (через переменные окружения или `.env`):

- `API_HOST` — адрес прослушивания, по умолчанию `127.0.0.1`;
- `API_PORT` — порт, по умолчанию `8080`;
- `API_OUTPUT_DIR` — папка для отчётов и журналов, по умолчанию `результаты`;
- `API_TOKEN` — необязательный токен доступа (только латиница и цифры). Если задан, каждый запрос к `/ask`, `/review`, `/extract`, `/diff`, `/penalty`, `/check`, `/timeline` и `/draft` требует заголовок `Authorization: Bearer <API_TOKEN>`. `/health` и `/openapi.json` остаются открытыми для проверок живости.

API-ключи модели и Tavily передаются только через переменные окружения и не попадают в ответы API.

docker build -t legal-research-agent .

Двести девяносто тестов проверяют разбор JSON, удаление дублей, структуру и ссылки ответа, подтверждение упомянутых статей в источниках, исправление ответа, самопроверку ответа (consistent/issues, исправление, деградацию при сбое), дополнительный поиск, обязательную проверку изменений, этап судебной практики, проверку договоров (контроль цитат, исправление, валидация), скоринг (веса, кэпы вычетов, вердикты), извлечение реквизитов (контроль цитат и идентификаторов, контрольные суммы ИНН/ОГРН), извлечение текста из DOCX (разбор ZIP/XML, таблицы, отклонение PDF, base64), реестр договоров (разбор дат, CSV, отчёт по срокам, обход папки), пакетный аудит (скоринг папки, сводный отчёт, устойчивость к ошибкам), сравнение редакций (added/removed/changed, unified diff), протокол разногласий (дословный контроль редакций, исправление, таблица), расчёт неустойки (договорной и по ст. 395 ГК РФ, разбивка по периодам ставок ЦБ), проверку контрагента (разбор ответа ФНС, признаки риска, повторные попытки), хронологию дела (валидация дат и цитат, сортировка, исправление), драфтинг документов (структура по типу, контроль цитат, плейсхолдеры), маршрутизацию запросов (допустимые категории, соответствие эндпоинта категории, исправление), расчёт госпошлины (обе шкалы, границы диапазонов, кэпы, судебный приказ, фиксированные пошлины), экспорт в DOCX (сборка пакета, таблицы, экранирование, круговая проверка через doctext), сессии (TTL, лимит записей), метрики (счётчики запросов и ошибок) и HTTP API (эндпоинты, OpenAPI, валидацию запросов и авторизацию по токену). Тесты не обращаются к внешним сервисам.

## Авторские права и происхождение правовых данных

- По умолчанию поисковый этап использует официальные государственные источники (`pravo.gov.ru`, `publication.pravo.gov.ru`); коммерческие справочные системы не входят в разрешённые источники поиска.
- Не загружайте в репозиторий PDF, базы, комментарии, подборки, аналитические материалы или экспорт из «КонсультантПлюс», «Гарант» и иных коммерческих сервисов без подтверждённых прав на такое использование.
- Официальный текст нормативного акта и охраняемые редакционные материалы вокруг него — разные объекты. Не копируйте аннотации, комментарии, составленные подборки, интерфейсные материалы и чужую структуру базы.
- Судебные акты и нормативные документы необходимо получать из законных первоисточников; соблюдайте правила доступа, ограничения автоматизированного сбора и требования к персональным данным.
- Файл `.gitignore` предотвращает случайное добавление новых PDF/DOCX/ZIP, но **не удаляет ранее опубликованные файлы и историю Git**. Перед публикацией репозитория требуется отдельный аудит всех веток, тегов, релизов, артефактов CI и истории коммитов.
- При обнаружении материалов с неясными правами прекратите их использование, ограничьте доступ и проведите правовую проверку до коммерческого распространения. Переписывание истории Git требует отдельного плана, резервного копирования и координации с участниками проекта.


## Реестр происхождения новых документов (этап 2)

Модуль \`source_admission.py\` проверяет URL первоисточника и минимальные метаданные. Разрешённые домены ограничены официальными порталами и отдельными судебными ресурсами; неизвестные и коммерческие домены отклоняются. Даже для официального источника модуль **не выдаёт разрешение на массовое копирование**: \`approved_for_full_text=False\`, а статус проверки прав остаётся \`pending\`.

Пример записи: \`{"document_id":"123","source_url":"https://publication.pravo.gov.ru/Document/View/123","fetched_at":"2026-11-12T12:00:00Z"}\`. Поля \`full_text\`, \`raw_content\`, \`pdf_base64\` блокируются. Это самостоятельный защитный шлюз; пока не подключены все существующие загрузчики и источники. До их подключения нельзя считать весь импорт защищённым.
